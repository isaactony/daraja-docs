title: "Fix \"Wrong credentials\" (500.001.1001)"
description: "Fix the Daraja STK Push error 500.001.1001 Wrong credentials: a Password that doesn't match the shortcode, passkey, or timestamp, and how to check yours."
---

```json
{
  "requestId": "...",
  "errorCode": "500.001.1001",
  "errorMessage": "Wrong credentials"
}
```

Despite the name, this isn't about your consumer key or secret. Your token worked, or you'd get `Invalid Access Token`. It means the STK Push or STK Query **`Password`** field doesn't match.

`Password` must be `base64(BusinessShortCode + Passkey + Timestamp)`, using the same `BusinessShortCode` and `Timestamp` values you send in the request body.

## Check your password code against the official sample

The official STK Push sample uses shortcode `174379`, the sandbox passkey, and timestamp `20210628092408`. Your function must produce exactly the sample `Password` from those inputs:

```text
MTc0Mzc5YmZiMjc5ZjlhYTliZGJjZjE1OGU5N2RkNzFhNDY3Y2QyZTBjODkzMDU5YjEwZjc4ZTZiNzJhZGExZWQyYzkxOTIwMjEwNjI4MDkyNDA4
```

```bash
printf '%s%s%s' 174379 "$DARAJA_PASSKEY" 20210628092408 | base64 | tr -d '\n'
```

If your output differs, the bug is in how you build the password. If it matches, the bug is in the values you pass in.

## Common causes

### The timestamps don't match

You generated one timestamp for the password and another for the `Timestamp` field, perhaps by calling your timestamp function twice across a second boundary. Generate it **once** and use the variable in both places.

### The timestamp format is wrong

It must be exactly 14 digits, `YYYYMMDDHHmmss`, with a 24-hour clock and leading zeros: `20261113093005`, not `2026-11-13 09:30:05` or `2026111393005`. In JavaScript, `getMonth()` is zero-based, so add 1.

### The passkey is for a different shortcode or environment

The sandbox passkey only works with `174379`. In production, use the passkey Safaricom emailed you after go-live, with the shortcode you went live with. Check for spaces or line breaks copied around the passkey.

### `BusinessShortCode` differs between the password and the body

For a till, both must be the store number. See [Paybills, tills, and shortcodes](/concepts/paybill-till-and-shortcodes).

### `base64` wrapped the output

On Linux, the `base64` command wraps output longer than 76 characters onto a new line. The password is longer than that. Add `| tr -d '\n'`, or use `base64 -w 0`.

### You copied the STK Query sample

The official STK Query sample `Password` is corrupted. See [Known doc discrepancies](/reference/known-doc-discrepancies).

## The same code with a different message

`500.001.1001` also means "Merchant does not exist" (the shortcode isn't valid for this app or environment) and "Unable to lock subscriber" (see [the fix](/troubleshooting/unable-to-lock-subscriber)). Read `errorMessage`.
